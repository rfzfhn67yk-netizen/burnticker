## Temporary powers (with sunset)

- **Platform burn-pool cap** — holder: platform_authority (the Squads 2-of-3 vault). While in force, each token's buyback spend is computed on min(pool, cap); SOL above the cap stays in the fee PDA and a BurnPoolCapBound event is emitted every time the cap binds. Default 25 SOL (25,000,000,000 lamports). Raise only, through propose_cap_raise → 48 h → apply_cap_raise. **Sunset:** PlatformConfig.cap_sunset_ts — set once at initialize_platform (at most 365 days out and no later than 2027-10-01), never extendable; after it the program ignores the cap. Also ends early in effect if the authority raises it to u64::MAX. *Why:* A pre-audit limit on how much SOL any single burn day can push through an unaudited program (owner decision, 2026-10-09).
- **Cranker allowlist (review-3 L-4)** — holder: set once by the upgrade authority at initialize_platform; clearable (never extendable) by platform_authority or by any listed key. While the cap is in force and the list is non-empty, only listed keys (≤ 3) may crank_buyback — against an outside cranker timing a multi-block TWAP hold. Readings, vault cranks, claims and health checks stay permissionless. Default Empty (permissionless).. clear_cranker_allowlist only (back to permissionless), by the platform authority or any listed key. **Sunset:** PlatformConfig.cap_sunset_ts or PlatformConfig.created_at + 90 days, whichever is first (re-check R3-4); afterwards crank_buyback is permissionless whatever the list says. *Why:* Against a multi-block TWAP hold timed by an outside cranker while the program is unaudited. If every listed key is lost and the authority renounced, buy-back cranks wait at most 90 days from initialize_platform (no funds move in the meantime).
- **Registration-policy switch — stranding recovery (review-3 M-3)** — holder: config_authority (TokenConfig.admin, the Squads vault). Switch a token whose LaunchLab migration cannot be registered (or whose pool died) to a fixed pool passing the creator + LP checks, or back to policy 0. Default Unused.. set_registration_policy → 48 h → apply_registration_policy (anyone) within 14 days of the proposal; cancel_registration_policy (admin); veto_registration_policy (any one current attester). A fallback fixed pool needs ≥ 90 % LP burned/locked or a LaunchLab-known AmmConfig (re-check R3-2). **Sunset:** The pre-audit cap's sunset (PlatformConfig.cap_sunset_ts, or 2027-10-01 without one); also gone at renounce_admin. *Why:* LaunchLab is closed source; its platform admin can change cpConfigId / platformCpCreator / lock scales before migration. Real LaunchLab behaviour remains a devnet-rehearsal gate.

## Roles

- **anyone** — Anyone with a funded wallet. Pays only the transaction fee (and rent where noted); chooses no amounts.
- **mint_keypair** — The holder of the new mint's keypair — the launchpad, inside the token's create flow. Usable exactly once per mint.
- **creator** — The creator wallet recorded at init. Holds no power by itself; it is the initial config authority.
- **config_authority** — TokenConfig.admin — initially the creator; can be renounced forever (renounce_admin). Powers: attester set only.
- **attesters** — The quorum (N of M) of attester ed25519 keys named in the TokenConfig — kind-tagged operator / zktls-relayer / oracle (informational). Each signs (feed, period, value, sha256 of the source URL, zkTLS proof locator); the program verifies only signatures and the quorum.
- **upgrade_authority** — The program's upgrade authority (BPF Upgradeable Loader). At launch: the Squads 2-of-3 vault; its time lock is 0 during launch week (owner decision 2026-10-11) and 48 h is planned from around 2026-10-23 — the live value is read from chain on /burnticker/trust; set to none after the audit.
- **platform_authority** — PlatformConfig.authority — intended: the Squads 2-of-3 vault. Power: RAISE the temporary burn-pool cap (48 h timelock). Renounceable; the cap sunsets by itself.
- **attester_key** — Any ONE key of the token's CURRENT attester set, signing a transaction by itself (no quorum). Power: veto (clear) a pending registration-policy proposal — nothing else (re-check R3-2).
- **platform_authority_or_listed_cranker** — PlatformConfig.authority (while not renounced) OR any key on the PlatformConfig's cranker allowlist (re-check R3-4). Power: clear the allowlist (back to permissionless) — never add a key.

## What does not exist

- No withdraw, sweep, transfer, close or set-recipient instruction exists for the fee PDA, its token accounts, the vault or any program account. SOL leaves the fee PDA only inside crank_buyback (into its own WSOL account, then into the CPMM pool for tokens that are burned) inside forward_to_winner (LAUNCHPAD-PATH §40: only to the paired winner's fee PDA, only the formula amount for an attested lost period) and inside forward_on_end (LAUNCHPAD-PATH §45: only after a quorum-signed RESOLVED end, only to the fee PDA of the end sink the program picks — the pinned coin while it is live, else the compiled flagship — never an amount or a destination the caller chooses) and inside burn_sol_on_end (round 5: only for a coin whose pinned end sink is the incinerator, only after a quorum-signed RESOLVED end, only to Solana's incinerator, address-checked) and inside crank_target_burn (round 5: only into the PINNED pool's WSOL vault, for the other token, burned in the same instruction); tokens leave only by burn.
- Round 5: no instruction changes the other token a coin burns; only the pool it is swapped on can be re-pinned (propose_target_pool → 48 h, any attester can veto → apply_target_pool, the same checks).
- No program account (TokenConfig, Reading, PlatformConfig, FeeKeyRecord, fee PDA) is ever closed. The only accounts the program closes are the FEE_KEYS PDA's own transient WSOL and token accounts inside claim_lock_fees, created and emptied in the same instruction, their rent back to the cranker who paid it (to the fee PDA if someone else created them); and, in burn_sol_on_end (round 5, the incinerator end sink), the fee PDA's own WSOL account, closed into the fee PDA to unwrap its WSOL and created again in the same instruction at the same address, the cranker's rent refunded from it.
- No pause or freeze exists. Nothing can stop cranks except the rule's own guards (a stale TWAP or a closed pool defers a burn day; it is never lost). The burn-pool cap limits how much of a pool one burn day may spend on; it never stops a burn.
- No instruction mints tokens, and none holds a mint authority: the program's only token instructions are Burn (and SyncNative on its own WSOL account). There is no team allocation in the program.
- No fee is charged by the program, so there is no fee to change. The LP-fee split of claim_lock_fees (80 % burn pool / 20 % operator) and the operator treasury are compiled constants: no instruction, config field or key changes them (LAUNCHPAD-PATH §35).
- No instruction moves the locked LP principal or the Fee Key NFT: the lock is Raydium's permanent lock, and FEE_KEYS signs only collect_cp_fees inside claim_lock_fees.
- No instruction updates the burn rule (RuleParams), the feed id, the memo text, the rules hash, the mint, the creator record or the registered pool.
- No instruction edits or deletes a reading; readings are append-only and quorum-checked.
- The quorum can never be lowered (nor exceed 3), the attester set can never be smaller than the quorum, and one proposal must keep at least `quorum` of the current keys and add fewer new keys than the new quorum; keys are added only on the strength of kept keys ≥ 7 days old.
- No instruction changes the pinned LaunchLab platform / cpConfigId; the registration policy changes only through set_registration_policy (48 h, stranding only, until the cap sunset), which can never select policy 2 (pair curve) — that policy is chosen at initialize_token or not at all.
- No PlatformConfig is required: without one, the hard-coded default cap (25 SOL until 2027-10-01) applies, so a lost or finalised upgrade authority cannot wedge buybacks.

## Program upgrade authority

- **power** — Program upgrade authority (BPF Upgradeable Loader) — outside the IDL, the one power that could change everything above.
- **holder_at_launch** — The Squads v4 2-of-3 multisig vault. Mainnet time lock: 0 during launch week (owner decision 2026-10-11, so deploy and config fixes are not delayed), 48 h (SetTimeLock 172800) planned from around 2026-10-23; once set, every upgrade is proposed publicly and waits 48 h before it can execute. The live value is read from chain (GET /api/burnticker/v1/current-status). The same vault holds the platform authority and, per token, the config authority.
- **sunset** — Set to none (`solana program set-upgrade-authority <PROGRAM_ID> --final`, executed through the multisig) after the audit — the program then can never change.
- **verify** — docs/burn-receipts/README.md § Deployment runbook: commands, `anchor verify` / `solana-verify` and the expected executable hash.

## Powers outside the program that it depends on

- **LaunchLab platform admin (Raydium LaunchLab PlatformConfig, outside burn_receipts)** — holder: the key that created the LaunchLab platform — not transferable (no admin-change instruction; the platform PDA is seeded by the admin key). Timelock: none (untimelocked key). Can: updatePlatformConfig: fee rate and wallets — including platformLockNftWallet, which receives every migration's Fee Key (LAUNCHPAD-PATH §35: burn_receipts' FEE_KEYS PDA) — cpConfigId, platformCpCreator, LP lock/burn scales (migrateCpLockNftScale; Burnticker: 1,000,000 / 0 / 0, all LP locked), vesting, curve rules — for launches that have not migrated yet. Effect here: Pinned at initialize_token (review-3 M-3): a later cpConfigId change cannot redirect register_pool (only replace_pool uses the platform's current cpConfigId, after 7 continuous days of a dead pool); platformCpCreator / scales and (LAUNCHPAD-PATH §35) platformLockNftWallet = FEE_KEYS with scales 1,000,000/0/0 are checked at init. Changing them between a token's init and its migration can still strand the registration (recovered with set_registration_policy, 48 h, until the cap sunset) or send that migration's Fee Key — and so its LP fees — to another wallet (the LP itself stays locked; the fees then never reach the burn pool). Since lp-lock blind review r2 (RL-3) such a coin fails closed: register_pool requires the FEE_KEYS-held migration position to be recorded, so its pool is never verified and no buyback runs on it; and initialize_token pins only the operator's compiled BURNTICKER_PLATFORM, whose admin key is the operator's (to move under the Squads vault). LAUNCH GATE (re-check R3-3): immediately before LaunchLab's create the launcher re-reads platformCpCreator, the scales, platformLockNftWallet and cpConfigId and refuses on any difference (`burnreceipts-admin.mts verify-platform-pins --mint`).
