### Actionable findings

#### F1. [P1] Fence newly planned receipts before submitting counter readings

**Pinned location:** [`scripts/burnticker-keeper.mts:180`](https://github.com/rfzfhn67yk-netizen/burnticker/blob/07b7b4f5dc8b3c639261c0abf1f04d30bf5737bb/scripts/burnticker-keeper.mts#L180).

New. The production cycle runs ops.beforeCycle (and readingFence) before runCycle fetches and plans receipts. A standby or restarted keeper with an empty local pending set therefore checks zero tokens, then plans events already submitted by another keeper and adds their units to the on-chain counter on the next date (multiKeeper.ts:455–466). This can spend the burn pool twice for one source event. A local two-registry reproduction using the shipped FakeBurnProgram and Treasury fixture produced checked=0, no hold, and counter 63→125 for the same source history. The existing fence test first plans B in dry-run, unlike the production order. Move the fence between planning and the first attestation, including pair attest-only and wind-down paths, and fail closed on unreadable config. Add a regression invoking the production order with an empty standby registry and assert no duplicate counter increment.

#### F2. [P1] Keep unlocked graduated pairs in the scan until recovery completes

**Pinned location:** [`src/lib/burnKeeper/pairCurveCrank.ts:95`](https://github.com/rfzfhn67yk-netizen/burnticker/blob/07b7b4f5dc8b3c639261c0abf1f04d30bf5737bb/src/lib/burnKeeper/pairCurveCrank.ts#L95).

#### F4. [P2] Retain sent launch signatures across ambiguous confirmation failures

**Pinned location:** [`src/lib/burnticker/signPlan.ts:92`](https://github.com/rfzfhn67yk-netizen/burnticker/blob/07b7b4f5dc8b3c639261c0abf1f04d30bf5737bb/src/lib/burnticker/signPlan.ts#L92).

### Money, authority and eventual-progress review

**LP and fees.** `burn_receipts/src/instructions/lock_fees.rs:113` registers the Fee Key with mint, token-account, locker and lock-position checks; the claim at line 265 fixes the treasury, uses the registered pool, and takes no caller-chosen partial amount. `constants.rs:282` fixes 8,000/2,000 bps. The token side is burned. The registration order and stored FeeKeyRecord address the prior redirected-fee-key and replacement-pool issues. Claim destinations are not arbitrary caller wallets. The rent return is distinct from operator fee income. Mainnet zero pins refuse initialization/claims until compiled addresses are set. These are code properties; no current mainnet configuration was verified. The advertised 30-day LP destruction recovery exists on chain but is not eventually executed by the current graduated-pair scan (F2). Ordinary graduation creates a pool before the separate lock transaction, so “locked at graduation” should expose the intermediate unlocked state.

**Pair signatures and money flow.** Current `pair.rs` checks the result date against pairing, requires both relevant readings and an unprocessed loser before accepting a win, uses the losing side's quorum, and requires the partner's co-signature if the losing attester set has changed. Draws require both. The destination is the winning coin's fee PDA; holders do not receive a distribution. A non-live side can produce a zero-lamport forward that still processes the loser reading. The missing-result and missing-forward paths have 72-hour burn fallback. This closes the old no-winner-reading/no-pool permanent queue wedge. F5 remains a different permanent registration failure. A losing side's attesters can still decline to sign its losses: the period then falls back to burning unpaired while wins may be accepted. This is the prior M-1 trust limitation, not a new unauthenticated theft finding. The 72-hour threshold does not by itself revoke the on-chain forward path; late forward versus fallback is a race until processing. Do not tell users “can never forward” merely because the clock elapsed.

**Keeper.** Fetching, planning and execution are separate in `multiKeeper.ts:693`. Active pair coins attest before the execution pass; losers execute before winners. Write-ahead signatures and adoption of processed readings are present, including the later foreign-forward adoption changes. Those improvements do not fix F1's fence placement. Independent binary/fixed-baseline events are deduplicated by identity instead of discarded solely by a cursor. Ordered scalar late readings are explicitly alerted and not safely retroactively replayed; a finite source-discovery window still limits catch-up. This report does not promise recovery from an arbitrary-length outage. Source failure/disagreement is intended to hold signing, while source correctness still depends on attesters: an on-chain signature check cannot establish that a factual claim was true.

**Launch and displayed consent.** The public browser cannot reach the signing card while the creator-launch gate is off. The card lists signer roles and per-step status, but the review card does not present an estimated aggregate SOL debit, account/rent breakdown, network, or complete pair-curve deadline/raise/minimum-side-share conditions before automatically opening the wallet prompt. `SignPlan` validates supplied mint keys against expected public keys; it does not independently decode every instruction into the displayed economics. The wallet is an additional review surface, not proof that the app's plain-language summary is complete. F3 and F4 prevent treating the new end-to-end signing UI as fully recovered from prior N6.

**HTTP, SDK and ops.** Creator launch routes have the default-off gate; legacy POST and v1 paths apply origin/rate controls. These controls are not authentication of launch content (F3). Ops access additionally requires its PIN; a Host-based network label alone is not identity. SDK verification now binds a program instruction, inner memo/burn and owned Reading rather than accepting arbitrary memo text (`packages/burnticker-sdk/src/verify.ts:68`). Export code rejects symlink/irregular sources and rechecks opened descriptors (`scripts/ops/public-repo-lib.mjs:326`); no private monorepo or live server environment was scanned. I did not publish a snapshot or exercise uploader funding. Deployment scripts were inspected; none was executed.

### Explanation mismatches that cut across routes

1. **Pair direction:** home and templates say the loser burns or no pool can pay the other; the current linked-pair rule sends the loser's calculated allocation to the winner's burn pool. Fix F6 before a visitor chooses a pair.
2. **Availability:** homepage, empty Coins, league teams and templates keep offering creation while the loaded launch page is closed. A shared availability state should suppress the action across all these entries.
3. **Proof scope:** “all receipts recompute” with zero receipts is vacuously true but not useful evidence. “Source only,” “recorded build,” “rehearsal” and “chain checked” need separate visible labels.
4. **Income provenance:** curve wallet chain reads, operator-entered expenses and LP keeper records are different evidence sources. Remove the fee ledger's universal “nothing ... from our own records” assertion.
5. **Host versus chain versus design:** show network, host program wiring, chain deployment, live config read, compiled constants and planned configuration separately; do not flatten them into one “not deployed” or “locked forever” label.
6. **Rule ends:** one-shot does not necessarily mean the supply stops changing immediately; use the actual `onEnd` and retirement schedule.
7. **Sources:** replace stale ESPN settlement labels with the actual primary/independent-check method; keep a human ESPN link labeled only as a viewing link. “Coverage” from fixtures is not current availability or a licence certificate.
8. **Security reports:** list ten report documents, distinguish embedded rechecks, include current residuals, and make the latest disposition visible before the historical log. None is a professional-audit guarantee.
9. **Launch cost/permission/recovery:** the plan's key check and number of decisions do not replace an estimated debit, transaction count, network and pending-signature recovery state.
10. **Ops data absence:** “could not be read” should remain unknown/unavailable. It is not proof that the keeper is merely between cycles or that receipts elsewhere are unaffected.
