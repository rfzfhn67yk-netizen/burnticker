### N1 — Public launch-confirmation replay changes an immutable economic baseline

**Evidence.** `registry.ts:309–313` rejects a different existing signature but permits the same one, then always writes the caller-supplied `baseline_at`. `api/handlers.ts:585–590` validates only signature shape and supplies the current server time. `multiKeeper.ts:140–141` filters all candidate readings against this baseline. The launch signature is public (`tokenPage.ts:270`). The handler's statement that the keeper verifies the launch transaction is not backed by a launch-transaction verification step in the inspected keeper path.

**Exploit.** Read a live token's mint and real launch signature; POST them to the public launch-confirm endpoint (or legacy `action: "launched"` route) before its next settlement cycle. Repeat with exactly the same signature. Each call advances the baseline and excludes earlier, unprocessed events, even if their readings are already in the registry. This needs neither the creator key nor a forged signature. A syntactically valid invented signature can also prematurely activate a draft and make its later legitimate confirmation conflict.

**Fix.** Verify the successful launch transaction against the expected mint, creator, program and configuration, derive baseline from its chain time, and permit only an atomic draft-to-live transition. Repeating the accepted signature must be a no-op. Protect baseline and launch identity with the registry's SQL immutability constraints.

### N2 — Runtime catalogue settlement omits independent corroboration

**Evidence.** `coverage/preflight.ts:106–121` obtains primary and cross-read during launch preflight. Production instantiates `CatalogueAdapter` in `scripts/burnticker-keeper.mts:100`. Its generic branch delegates straight to `feed.settledSince` (`catalogue/index.ts:149–157`); `sources/attestedHttp.ts:230–235` fetches/parses the configured primary. `multiKeeper.ts:120–123` persists these events as readings, and its signing path at `311–330` uses them without rerunning corroboration. Native adapters have different logic; this finding concerns the generic HTTP catalogue path. A concrete configured pair is BLS eggs and the FRED eggs cross-read (`config/burnticker/sources.json:10`, `:124`).

**Exploit.** Let a token pass preflight while both sources agree. Later have the primary publish a plausible but wrong value, or let the cross-read fail/disagree while the primary remains available. The keeper still accepts the primary reading and signs the resulting units; the official launch defaults to one attester (`api/handlers.ts:532`). An upstream compromise or ordinary erroneous publication can therefore produce an irreversible burn without the promised independent confirmation. On-chain signature checks faithfully authenticate that decision; they do not repair its missing data check.

**Fix.** Before persisting an attestable event, read the independent source for the **same fact and period**, apply a defined agreement rule, and hold on missing/disagreeing data. Preserve both source values, times and provenance in the public proof. A successful historical launch preflight is insufficient.

### N3 — SDK verification does not bind a memo to a burn

**Evidence.** `packages/burnticker-sdk/src/verify.ts:34–42` takes the first memo-shaped log from a successful transaction. It does not require the expected burn program, mint, Reading account, or SPL burn instruction. `src/lib/burnticker/verify.ts:119–127` uses transaction success and equality of that memo as its chain checks. In contrast, the main program client uses provenance-aware `memoFromTransaction` (`src/lib/burnReceipts/crank.ts:92`).

**Exploit.** Construct a self-consistent receipt using a real public event and matching rules/units, send its claimed memo in an ordinary Memo-only transaction, and supply that signature to SDK verification. The source and arithmetic can pass and the memo matches, although no tokens were burned. An application trusting the SDK's verified result can display nonexistent burns.

**Fix.** Require expected mint/program identifiers and verify a program-owned processed Reading plus the actual program-invoked burn/memo and amounts. Reuse the hardened client's provenance handling where appropriate. Missing chain identity must remain unverified. Add a memo-only negative case to the SDK, since the earlier F10 correction covered a different consumer.

### N4 — Unmetered legacy launch consumes the platform uploader balance

**Evidence.** `src/app/api/burnticker/launch/route.ts:16–24` checks same-origin and directly calls `prepareLaunch(..., {register:true})`, bypassing the v1 limiter. `api/handlers.ts:517–529` pins rules/metadata with the configured funded uploader before a wallet has signed or completed the launch. Draft registration is also performed (`:534`).

**Exploit.** On a deployment with paid uploads enabled, repeatedly POST otherwise valid fresh tickers and selectors with a matching Origin header, then abandon every wallet launch. A nonbrowser client can set that header. Each request can spend platform upload funds and create drafts; the v1 rate limit does not constrain this route.

**Fix.** Put the legacy route behind the same shared write/heavy-operation limits and upload quotas. Bind expensive pinning to authenticated wallet intent and a durable funding/launch commitment, or charge the requester. Origin checks address browser cross-site requests, not direct abuse.

### N5 — Export path allowlisting does not confine symlink targets

**Evidence.** `scripts/ops/public-repo-lib.mjs:58–68` builds file lists without rejecting symlinks; overlay enumeration at `:79–85` also includes them. Binary exclusion is extension-based (`:151–154`). Reads and the export `copyFileSync` (`:254`) follow the target, with no regular-file/realpath confinement.

**Exploit prerequisite and steps.** A publishing checkout or overlay contains an allowlisted symlink, for example `site/burnticker/private.png` pointing to private source outside the allowed tree. It can arise from a malicious commit or a local publishing mistake. The allowed pathname passes; the `.png` extension skips the text deny scan; copying publishes the target bytes as an ordinary file. This is a publisher-filesystem boundary flaw, **not** a demonstrated remote web exploit or an observed leak in this snapshot.

**Fix.** Reject symlinks, including symlink ancestors, during manifest construction and copy, and require regular files whose resolved paths stay inside the approved source root. Apply equivalent checks to overlays and rescan the actual staged output. Filename allowlisting and deny regexes cannot prove content provenance.

### N6 — Wizard still launches two independent LaunchLab bundles when pair curve is enabled

**Evidence.** `api/handlers.ts:566–567` builds the optional pair-curve transaction bundle when `BURNTICKER_PAIR_CURVE_ENABLED` is true, alongside the old LaunchLab bundles. The legacy endpoint serializes selected fields and omits `pairCurve` (`launch/route.ts:27`). The wizard calls that endpoint and selects `j.bundles.a/b` (`src/app/burnticker/launch/page.tsx:354–364`). Draft token addresses also come from the original LaunchLab bundle (`handlers.ts:534`).

**Exploit/failure scenario.** Enable the flag and create a paired launch through the normal wizard. It still offers independent LaunchLab transactions. One can land while the other is abandoned; the new Pair commitment, shared graduation and redemption protections never govern those launches. This undermines the intended both-or-neither behavior without attacking the Rust program.

**Fix.** Select the venue end-to-end: serialize and sign the pair-curve transaction set, store the corresponding on-chain pair/mint/pool configuration, and make the UI explicitly use that result. Refuse the unsupported route while the feature is enabled instead of silently falling back.

### N7 — Late finality is discarded by a global timestamp cursor

**Evidence.** `multiKeeper.ts:114–116` deliberately fetches an overlap window, but `:140–141` requires every unseen event to be strictly after `lastSettledAt` (or later by ID on the same timestamp). Polymarket preserves Gamma's closed/end timestamp (`oracle/polymarket.ts:189–190`) while holding an unresolved CTF payout and retrying it later (`:207–218`).

**Exploit/failure scenario.** Event A closes on day one but its final payout or a source read is delayed. Event B closes and settles on day two and advances the token cursor. A becomes final on day three and is fetched within the overlap window; it is stored but forever excluded from planning because its original timestamp precedes B. Natural delays suffice; an upstream actor able to delay one event can selectively suppress its burn. A newly discovered same-time event with an earlier ID is similarly omitted.

**Fix.** For independent binary events, use per-event processed identity and an explicit launch/window boundary, not a latest-event watermark. For ordered scalar feeds, implement a documented completeness/backfill/correction policy that preserves carry semantics; do not simply process older scalar values against the newest baseline.

Two residual scenarios qualify “all fixed” without re-reporting the old vulnerabilities as new:

- **Deadline-to-void ordering (Medium, residual of R2 M-1).** `PC/instructions/trade.rs:44` explicitly allows curve sells past deadline until `void_pair` lands, and `:140–149` implements that. A holder can sell at the then-higher curve price just before the void snapshot, reducing the remaining pro-rata pool. Already-Voided redemptions are correctly fee-free and order-independent; the race is at the state transition. If fairness is promised from the deadline, make the first post-deadline sell enter redemption atomically, or reject until void. If fairness starts only at the explicit snapshot, disclose that boundary and retain it as an accepted economic risk. The checked-in comment indicates intentional semantics, not a missing status branch.
- **Unsynced own WSOL ATA donation (Low, retryable grief).** Pair graduate samples stored WSOL amount (`graduate.rs:146`) before SyncNative (`:151`), then compares the post-CPI remainder to the old amount (`:196`). A lamport transfer to an already-created pair-vault WSOL ATA without SyncNative makes this equality stale and can fail graduation. Anyone can synchronize it to recover; it is not a permanent lock. Synchronize before sampling, or derive the effective initial balance from lamports/rent. The current keeper's graduate action does not prepend that recovery (`src/lib/pairCurve/client.ts:288`). This differs from the fixed destination pool-vault donation case.
