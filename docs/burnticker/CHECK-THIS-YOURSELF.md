What does not exist, in the registers' own words:

- (burn_receipts) No withdraw, sweep, transfer, close or set-recipient instruction exists for the fee PDA, its token accounts, the vault or any program account. SOL leaves the fee PDA only inside crank_buyback and crank_carried (into its own WSOL account, then into the CPMM pool for tokens that are burned) inside forward_to_winner and inside forward_on_end and inside burn_sol_on_end (: only for a coin whose pinned end sink is the incinerator, only after a quorum-signed RESOLVED end, only to Solana's incinerator, address-checked) and inside crank_target_burn (: only into the PINNED pool's WSOL vault, for the other token, burned in the same instruction) and inside release_target (round-5 review R5-6: only a stalled target coin's carried spend, only to the compiled flagship's fee PDA); tokens leave only by burn.
- (burn_receipts) No instruction changes the other token a coin burns; only the pool it is swapped on can be re-pinned (propose_target_pool, then 48 h, any attester can veto, then apply_target_pool, the same checks).
- (burn_receipts) No program account (TokenConfig, Reading, PlatformConfig, FeeKeyRecord, fee PDA) is ever closed. The only accounts the program closes are the FEE_KEYS PDA's own transient WSOL and token accounts inside claim_lock_fees, created and emptied in the same instruction, their rent back to the cranker who paid it (to the fee PDA if someone else created them); and, in burn_sol_on_end (the incinerator end sink), the fee PDA's own WSOL account, closed into the fee PDA to unwrap its WSOL and created again in the same instruction at the same address, the cranker's rent refunded from it.
- (burn_receipts) No pause or freeze exists. Nothing can stop cranks except the rule's own guards (a stale TWAP or a closed pool defers a burn day; it is never lost). The burn-pool cap limits how much of a pool one burn day may spend on; it never stops a burn.
- (burn_receipts) No instruction mints tokens, and none holds a mint authority: the program's only token instructions are Burn (and SyncNative on its own WSOL account). There is no team allocation in the program.
- (burn_receipts) No fee is charged by the program, so there is no fee to change. The LP-fee split of claim_lock_fees (80 % burn pool / 20 % operator) and the operator treasury are compiled constants: no instruction, config field or key changes them .
- (burn_receipts) No instruction moves the locked LP principal or the Fee Key NFT: the lock is Raydium's permanent lock, and FEE_KEYS signs only collect_cp_fees inside claim_lock_fees.
- (burn_receipts) No instruction updates the burn rule (RuleParams), the feed id, the memo text, the rules hash, the mint, the creator record or the registered pool.
- (burn_receipts) No instruction edits or deletes a reading; readings are append-only and quorum-checked.
- (burn_receipts) The quorum can never be lowered (nor exceed 3), the attester set can never be smaller than the quorum, and one proposal must keep at least `quorum` of the current keys and add fewer new keys than the new quorum; keys are added only on the strength of kept keys ≥ 7 days old.
- (burn_receipts) No instruction changes the pinned LaunchLab platform / cpConfigId; the registration policy changes only through set_registration_policy (48 h, stranding only, until the cap sunset), which can never select policy 2 (pair curve) — that policy is chosen at initialize_token or not at all.
- (burn_receipts) No PlatformConfig is required: without one, the hard-coded default cap (25 SOL until 2027-10-01) applies, so a lost or finalised upgrade authority cannot wedge buybacks.
- (pair_curve) No admin, authority, owner or operator field exists in the program; no instruction takes a privileged signer after init_pair.
- (pair_curve) No instruction updates a pair's parameters (virtual reserves, curve supply, target, minimum share, deadline, fee, fee recipients, AmmConfig) after init_pair.
- (pair_curve) No withdraw, sweep or transfer-out instruction exists for the SOL vault or the token vaults. SOL leaves the vault only as a seller's formula proceeds, the fee legs (fixed recipients, formula amounts), the CPMM deposit at graduation (formula amounts; the LP is then locked forever by lock_lp, — or, only if lock_lp cannot run for 30 days, burned by burn_lp) and residue to the burn pools.
- (pair_curve) No pause or freeze exists. Buys end at the deadline; nothing can stop sells on an open or voided pair.
- (pair_curve) No mint authority survives init_pair and no freeze authority ever exists; the program never mints after init.
- (pair_curve) The pair program holds the 75 bps burn share only in escrow: it reaches the side's burn_receipts fee PDA when the pool is created, or goes back to that side's holders on a void.
- (pair_curve) No trade credits any account but the SOL vault and the trader: the developer's 25 bps accrue in the vault (claim_developer_fee) and the 75 bps burn share is escrowed there until the side's pool exists — so neither the developer wallet nor a burn pool can block a trade or an exit.
- (pair_curve) The developer wallet is the claim wallet of the ONE LaunchLab platform compiled into the build (BURNTICKER_PLATFORM); a creator cannot route the 25 bps elsewhere.
- (pair_curve) A committed or graduated pair is never closed, so burn_receipts can always register its pools.

## 3. What is locked

- **Each coin's rule**. The burn rule, the data feed, the memo text and the hash of the rules file are written once, when the coin is set up (initialize_token). No instruction can change them. A different rule means a different coin. The rules file's sha256 hash is stored on chain (TokenConfig.rules_sha256) and appears in every memo. *Where:* docs/burn-receipts/powers-register.json, under non_powers
- **Readings and receipts**. Readings can only be added. The program checks the signers on chain before it stores one, and no instruction edits or deletes a reading. Off chain, the registry database uses SQL triggers to refuse edits and deletes. *Where:* docs/burn-receipts/powers-register.json, under submit_reading
- **Where a burn pool can trade**. Each coin's pool is registered once, after its origin is checked, and then it is frozen. A dead pool can be replaced only after 7 days in a row on record in which it could not trade, and the new pool must pass the same checks. *Where:* docs/burn-receipts/powers-register.json, under register_pool and replace_pool
- **Supply**. Neither program keeps the power to mint after a coin is created. Pair coins lose their mint authority inside init_pair, and they never have a freeze authority. The only token instruction either program runs on a coin is Burn. *Where:* docs/burn-receipts/powers-register.json and docs/burn-receipts/pair-curve-powers-register.json, under non_powers
- **Liquidity**. The liquidity pool tokens (LP) are locked forever at graduation. LaunchLab coins lock 100% when they move to their pool, under the platform config. Pair coins lock 100% through the pair program's lock_lp. Both use Raydium's LP lock, which can never be withdrawn. The Fee Key is held by an account that the burn program controls. Anyone can call claim_lock_fees. It pays 80% of the SOL-side fees to the coin's burn pool and 20% to the operator treasury, and those shares are fixed in the code. The coin side of the fees is burned. *Where:* docs/burn-receipts/powers-register.json, under claim_lock_fees; docs/burn-receipts/pair-curve-powers-register.json, under lock_lp; src/lib/burnticker/lockFees.ts
- **A pair's terms**. The curve settings, the combined raise that graduates the pair, the minimum share, the deadline, the fee and who receives the fee are all fixed when the pair is created (init_pair). The pair program has no admin at all. *Where:* docs/burn-receipts/pair-curve-powers-register.json, under non_powers
- **Coin metadata** (arweave at launch (in use on mainnet since 2026-10-13)). Each coin's metadata file and its art are uploaded to Arweave at launch. The metadata holds the name, the ticker, the image and the generated description, byte for byte. The token URI is the Arweave address. LaunchLab creates the metadata so it cannot be changed (is_mutable = false), and a launch is refused if the upload fails (src/lib/burnticker/pin.ts). The mainnet coins use it: $DEFICIT's metadata, created on 2026-10-13, is at https://gateway.irys.xyz/4dfxjEwmnfLjKaUbdpn2SGffS6jk9r1eKbnqRSxKXk6T (docs/burnkeeper/evidence/mainnet-deficit-2026-10-13/launch.json). The devnet rehearsal coins came before it, so their metadata is hosted on our server. The rule, the mint and the burns never depended on it. *Where:* config/burnticker/transparency.json, under trustPack.metadataUri

## 6. Verify a receipt

On the page, paste a receipt's transaction signature, or pick a devnet receipt. Each check shows ✓ when it passed, ✗ when it failed, or – when the page cannot run it, with the reason. These are the checks:

- The transaction exists and succeeded.
- It ran the pinned program's `crank_buyback`.
- The memo can be read.
- The Reading account, which the program owns, agrees with the memo.
- The TokenConfig belongs to that Reading.
- The published rules file hashes to the rules hash on chain.
- The Reading's `source_url_hash` is the sha256 of the Treasury URL for that date, and the Treasury API gives the same two values.
- The units come out the same when worked out again.
- The spend comes out the same in the program's fixed-point arithmetic.
- The transaction's Burn instructions burned exactly what the swap bought.

You can also check without the page. `curl -s https://burnticker.com/api/burnticker/v1/check/receipts` lists the devnet receipts. `curl -s https://burnticker.com/api/burnticker/v1/check/receipts/<signature>` runs the same checks on our server, with the same code (src/lib/burnticker/trustpack/receiptCheck.ts).
